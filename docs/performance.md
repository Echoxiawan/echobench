# 性能与硬件占用

## Android

Android 默认最高 30 FPS、长边最高 1280 像素、4 Mbps。H.264 在 Android 设备侧编码，浏览器通过 WebCodecs 解码；主要电脑开销来自浏览器视频解码、Appium 和控件树解析。

为规避部分显卡/浏览器组合在硬件 H.264 解码时输出纯黑画面，当前固定使用软件解码，720p 下 CPU 占用会比硬件解码略高。

页面静止时，Android 编码器可能降低出帧频率；浏览器保持最后一帧，这是正常节流。设备发生动画或操作后，流会继续推进。实时帧只存在于内存，不会持续写入硬盘。

## iOS

iOS 默认 15 FPS、60% 缩放、JPEG 质量 50。WDA 需要连续截图和 JPEG 编码，通常比 Android H.264 占用更多 CPU 和 USB 带宽。

### iOS 操作延迟优化

XCUITest 默认会在每个命令前等待页面 idle 最多 2 秒，而且 iOS 单次 `page source` 通常需要约 3–4 秒。当前实现做了以下优化：

- 会话创建时设置 `waitForIdleTimeout=0`、`animationCoolOffTimeout=0`，控件树深度设为 30，只排除 `enabled/accessible/index/processId/bundleId`，保留 `visible` 用于过滤不可见节点；单次 source 仍可保持在约 1 秒；
- iOS 空闲时**不轮询**，避免 WDA 被 source 请求占满；只有录制期间才会在每次操作后刷新一次控件树，非录制操作保持原有低负载；
- 录制点击使用“上一次操作之后”的缓存树，并用 Appium 实时校验主定位器；页面跳转较快、缓存尚未更新时会先等待刷新再记录；
- 元素拾取、“按坐标重新识别”和手动“刷新控件树”使用最新 page source，保证人工定位准确；
- iOS MJPEG 缩放调整为 50%、JPEG 质量 45，减少视频流数据量；
- iOS MJPEG 首帧后主动解除“正在连接视频流”遮罩，避免误判为连接失败。

因此 iOS 点击不会再固定等待 3–4 秒，非录制状态仍保持“交互优先”。录制状态下，页面跳转后的第一次点击会等待控件树刷新，之后每个点击还要经过一次 Appium 实时校验，所以会比纯操作略慢，这是为了保证回放定位器可靠。受 WDA 架构限制，iOS 仍会比 Android 的 ADB 直连慢一些。

## 多端同步

- Android 每设备独立 scrcpy 流，默认 960 长边 / 15 FPS / 2 Mbps；
- iOS 每设备独立 Appium/XCUITest 会话和 MJPEG 端口，画质更低；
- 全部实时会显著增加 CPU 和 USB 带宽；超过 2 路会提示；
- 单次最多 8 台设备，iOS 多设备首连需要为每台设备构建 WDA，耗时明显长于 Android。

## 自绘数字键盘

部分 App 使用自绘键盘，键盘按键本身是可点击控件，但输入框在深层控件树里。当前实现会：

- 用 active element 构造输入步骤目标，不再逐个记录键盘按钮的 tap；
- 把连续按键合并成一条 `input` 步骤，回放时直接清空并输入最终值，不依赖键盘是否展开；
- 开始记录时自动刷新一次控件树。

因此旧版本录制出来的、充满键盘按键 tap 的脚本需要重新录制。

如果键盘输入一直提示“当前没有聚焦的输入框”，通常是因为 `snapshotMaxDepth` 太小，把深层的 `XCUIElementTypeTextField` 裁掉了，`element/active` 也随之找不到。本项目默认使用深度 30 并排除无关属性；仍异常时可在日志中确认 `element/active` 是否返回元素，或重新连接会话。

## 硬件建议

- Android 单设备：普通开发机即可，主要开销在浏览器解码和 Appium；
- 多端同步：建议 16 GB 以上内存，iOS 多设备需要更多 CPU 和 USB 带宽；
- iOS 首次连接需要编译 WebDriverAgent，磁盘和 CPU 会有短暂高占用；
- 设备画面是实时流，不会持续写入磁盘；日志按大小轮转。
